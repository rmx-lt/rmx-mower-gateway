# Mower-Gateway: rmx-mower-gateway

Part of **Blade of Grass** (open-source robotic mower). Firmware for
the cellular link of the rmx-mower: an ESP32 + SIM7600G-H board that connects over LTE
to **rmx-server** and talks to **rmx-server-app** with **MQTT over TLS** only.

- Hardware: LilyGo T-SIM7600 (ESP32-WROVER-E N16R8, SIM7600G-H)
- Framework: ESP-IDF v6.1, esp_modem (PPP), mbedTLS, esp-mqtt
- Server: `mqtts://mqtt.rmx.lt:8884` (client certificate)

## Status

Firmware working on the hardware: over LTE (PPP) it logs in to the broker with its
client certificate (name = certificate CN, e.g. `mower-01`) and speaks the gateway's side of
[Mower-Protocol](Mower-Protocol) (issue 61, verified 2026-11-15, see [Mower-Gateway-Server-Contract](Mower-Gateway-Server-Contract)):
the retained status `mower/<name>/gateway/status` (last will `offline`), the retained `gateway/state`,
the metric catalogue `gateway/metrics/…`, `gateway/telemetry` (signal, system, data usage), commands on
`gateway/cmd` with acks on `gateway/cmd/ack`, monitor streams on `gateway/monitor`. A new image is requested as MQTT
chunks on `gateway/fw/req` and written from `gateway/fw/chunk`. Clean session, keep-alive 15 s. The firmware has no HTTPS
client. The NTRIP client and the link to the autopilot board are not in the firmware yet (other issues).
Verified 2026-11-15 on the board over LTE against the deployed server ([issue 65](https://github.com/rmx-lt/rmx-mower-gateway/issues/65)),
commands sent through the server's API:
an `ota` from 0.3.0 to 0.4.0 (749568 bytes) downloaded over `gateway/fw`, restarted into `ota_1` and sent the final `done`
ack with the same command id 2 minutes after the command;
an image built with an unreachable broker port did not confirm, 0.4.0 booted again and the command ended `failed` with
`rolled_back` 7 minutes after the command (300 s confirm time);
a monitor stream with `hold` 60 stopped 10 s after `mower/status/server` went `offline` and did not start again when the
server came back 24 s later.
Older text below that names the unprefixed topics (`mower/<name>/status`, `cmd`, `fw/…`) describes firmware up to 0.3.x. Verified 2026-11-10: a USB flash of 0.3.0 passed the MQTT self-test, an unknown
file returned `not_found` and left 0.3.0 running, and `ota` of `0.3.1.bin` (729088 bytes,
178 chunks) wrote the image, matched the chunk-header SHA-256, rebooted into `ota_1`, and
confirmed on the first MQTT connect. A reset at 10% was a clean retry from the first chunk.
Verified 2026-11-11: with the certificate as the only login (no password code left), the board
booted 0.3.3 after an OTA from 0.3.2, logged `login: client certificate` and passed the MQTT self-test.
The records protocol (`create`/`list`/`delete` on `mower/<name>/req|res`) and the "probe" naming were
removed in [issue 52](https://github.com/rmx-lt/rmx-mower-gateway/issues/52) (the server dropped them).
The old "self-test" log lines are now `mqtt connect: PASS` and `STARTUP OK`; Kconfig options are
`CONFIG_GATEWAY_*` (menu "rmx gateway"), the PlatformIO env is `gateway`, the project `rmx_mower_gateway`.
NVS keys (`creds/key`, `creds/chain`) did not change. The older "self-test" notes below are history.
Details: [Mower-Gateway-Plan](Mower-Gateway-Plan).

## Build, configure, flash (PowerShell)

PlatformIO is the main tool (since 2026-11-14); `idf.py` is a fallback, see [Mower-Gateway-Tools](Mower-Gateway-Tools).

```powershell
$pio = "$env:USERPROFILE\.platformio\penv\Scripts\pio.exe"
& $pio run -e gateway                  # build + sign (needs keys\ota_signing_key.pem)
& $pio run -e gateway -t menuconfig    # "rmx gateway": APN, broker URL (no logins, no passwords)
& $pio run -e gateway -t upload        # flash on COM6
& $pio test -e native                  # host unit tests of components/rmx_codec (needs gcc on PATH; CI runs them on every PR)
tools\provision_cert.ps1 -Name mower-02   # new board: CSR with that name, sign it, store the certificate (wiki Device-CA)
python -I -u tools\serial_log.py COM6 120 --until STARTUP
```

### Identity: client certificate only

One image fits every board; the identity lives in the board's NVS partition (`creds` namespace).
[Issue 43](https://github.com/rmx-lt/rmx-mower-gateway/issues/43). Verified on the board: the key,
CSR, chain write and clear 2026-11-10; the live login on 8884 with the real CA (cert serial 01,
CN `mower-01`), the self-test and an OTA to 0.3.2 over MQTT 2026-11-11; the password code was removed
afterwards and 0.3.3 (without it) arrived by OTA with the key and chain untouched, logged
`login: client certificate` and passed the self-test (2026-11-11).

- `key`: ECDSA P-256 private key (PEM), generated by the board at first boot (PSA, with the ADC
  noise source on because no radio feeds the ESP32 RNG), never printed or sent. Survives reboots,
  `idf.py flash` and OTA. Lost only with `erase-flash`.
- `chain`: PEM, device certificate followed by the issuing CA certificate (`<name>.chain.pem` of
  `device-ca.ps1 sign`, wiki Device-CA). The firmware accepts it only when the subject is a single
  valid CN (`[A-Za-z0-9_-]{1,32}`) and the certificate matches the key.
- The device name is the certificate CN and nothing else: no NVS `device`, no Kconfig default. A
  blank board has no name until it gets a certificate, so the name for the first CSR is given to
  `tools\provision_cert.ps1 -Name <name>`, which sends `RMX-CSR <name>`; the board does not store it.
- Boot without a valid `chain`: the board logs `no client certificate: not connecting` every 30 s,
  starts no modem and no MQTT, and waits for provisioning on the serial port.
- Boot with `chain`: MQTT goes to `CONFIG_GATEWAY_MQTT_CERT_URI` (default `mqtts://mqtt.rmx.lt:8884`)
  with `credentials.authentication.certificate` = chain and `.key` = key, no password; username and
  client id are the CN. The server is checked against the ISRG bundle.
- Serial commands (UART0, 115200, one line each): `RMX-CSR <name>` prints a CSR with CN `<name>`
  (`RMX-CERT-ERR name` if invalid); `RMX-CERT-BEGIN` / PEM lines / `RMX-CERT-END` stores a chain
  (answer `RMX-CERT-OK <cn>` or `RMX-CERT-ERR <reason>`, then restart); `RMX-CERT-CLEAR` deletes
  `chain` and restarts. They write only the `chain` key, so the key stays. Anyone with the serial
  port can replace or remove the certificate but cannot read the key. Flash and NVS encryption (key
  theft from a stolen board) is a follow-up.

Provisioning a new board end to end (needs the device CA, wiki Device-CA, and its passphrase):

1. `pio run -e gateway -t upload` (or `idf.py -p COM6 flash`). The board makes its key and waits.
2. `tools\provision_cert.ps1 -Name mower-02`: resets the board, asks for the CSR, runs
   `device-ca.ps1 sign` (asks for the issuing passphrase), sends the chain over serial.
3. The board answers `RMX-CERT-OK mower-02`, restarts, logs `login: client certificate` and
   connects. The broker side (ACL `mower/%u/#`, CRL) needs no per-device password.
4. `python -I -u tools\serial_log.py COM6 120 --until STARTUP` shows the startup.

Verified 2026-11-11 on the existing board: `RMX-CSR mower-01` gives a CSR with CN `mower-01` (`openssl
req -verify` OK) and an invalid name is refused. Not verified on hardware: the blank-board path (no
certificate, no connection) and the first CSR with `-Name`, because proving it would mean removing
the working board's certificate.

TLS trusts only ISRG Root X1 + X2 ([`certs/rmx-ca-bundle.pem`](https://github.com/rmx-lt/rmx-mower-gateway/blob/development/certs/rmx-ca-bundle.pem)), not
ESP-IDF's full Mozilla bundle. An `sdkconfig` made before 0.2.3 still has the full bundle:
in menuconfig, *Component config → mbedTLS → Certificate Bundle*, set *Default certificate
bundle options* to *Use no default certificates bundle* and enable *Add custom certificates
to the default bundle* with path `certs/rmx-ca-bundle.pem` (or copy the four TLS lines from
`sdkconfig.defaults` into `sdkconfig`).

## Send a command from the PC

```powershell
tools\mqtt_cmd.ps1 ping
tools\mqtt_cmd.ps1 restart
tools\mqtt_cmd.ps1 ota -Version 0.4.0 -Size 851234   # file = 0.4.0.bin; see "Firmware updates"
tools\mqtt_cmd.ps1 monitor_start -Session m-1 -Metrics usage.total.up,usage.total.down -Rate 2 -Hold 20
tools\mqtt_cmd.ps1 monitor_stop -Session m-1
tools\mqtt_cmd.ps1 ping -Id c-1 -Repeat 1       # the same id twice: the same ack twice
tools\mqtt_watch.ps1 -Seconds 120               # state, catalogue, telemetry, monitor, acks
```

Commands: `ping restart ota monitor_start monitor_stop` ([Mower-Protocol](Mower-Protocol) §5, §6.4, §15; details in
[Mower-Gateway-Server-Contract](Mower-Gateway-Server-Contract)). Each carries
`expires_at` (now + `-TtlS`, default 60 s). `status` and `gps` were removed (the modem's GNSS is not used; the data
is in `gateway/state` and `gateway/telemetry`). `ntrip_set`, `ntrip_clear` and `autopilot_reset` are other issues
(`unknown_cmd` / `failed`). The scripts log in as `app`; the broker forces client id `app`, so two of them at the same
time disconnect each other. Needs the Mosquitto clients for Windows and `ssh rmx-vps`.

## Firmware updates (OTA)

The device downloads a new image as MQTT chunks into the spare app slot (`partitions.csv`:
two 4 MB slots), checks it, boots it, and keeps it only if it reaches the MQTT broker within
`CONFIG_GATEWAY_OTA_CONFIRM_S` (300 s). Otherwise the previous image boots again. Code:
[`main/ota.c`](https://github.com/rmx-lt/rmx-mower-gateway/blob/development/main/ota.c).
The byte layout is wiki [Server-App](Server-App#firmware-over-mqtt). The device side is
[Mower-Gateway-Server-Contract](Mower-Gateway-Server-Contract).

- **Project name.** The project is now `rmx_mower_gateway` (was `rmx_mower_modem_probe`). The project-name
  check in `ota.c` accepts that one rename: a board still running the old name may update to an image named
  `rmx_mower_gateway`; after that the names must match as before.
- **Signed images.** OTA images must be signed with our RSA-3072 key (Secure Boot V2 scheme,
  `CONFIG_SECURE_SIGNED_APPS_NO_SECURE_BOOT` and `CONFIG_SECURE_SIGNED_ON_UPDATE_NO_SECURE_BOOT`).
  `esp_ota_end` checks that signature before `esp_ota_set_boot_partition`. The running
  firmware only accepts an update signed with the same key as itself. There is no hardware
  Secure Boot: no eFuses are burned, and USB flashing works as before.
- **Whole-image SHA-256.** Every chunk header carries the SHA-256 of the file. The device
  hashes the bytes it wrote and compares them before `esp_ota_set_boot_partition`.
- **File name.** The `ota` command's `version` selects `<version>.bin`, a file in the server's
  firmware folder (wiki [Server-Infra](Server-Infra#firmware-images-ota) §10). An optional `file` names the file
  instead (the legacy `url` is gone). The device does not open HTTPS.
- **Report.** The final ack comes from the new image (Mower-Protocol §6.5): the command id is kept in NVS across the
  restart; once the new image has confirmed itself and the server link is up it sends `done` with
  `{"version","previous","partition"}` (`previous` also shows in `gateway/state`: the image stores it when it confirms, and the first state on the server-link edge waits for that, so no state after an update has `"previous": null`; issue 108, verified 2026-11-20: OTA 0.4.0-pr108a → pr108b gave one state with `previous` 0.4.0-pr108a, then the `done` ack). If the new image does not confirm,
  the old one boots again and sends `failed` with `rolled_back`. The retained `mower/<name>/firmware` topic is gone.
- **Retries.** One chunk request is open at a time. After 10 s without an answer the same chunk is requested again
  with a new request id, up to 5 times in a row; then the update ends with `download_failed` (so does an error
  answer from the server). Bytes already written stay. A reset of the board drops the progress; the next `ota`
  command starts again. The running firmware is untouched until the whole image checks out.
  Verified 2026-11-19 (issue 15): a 60 s radio outage mid-download resumed at the missing chunk and finished; a 15-minute
  outage ended `download_failed` after the 5 retries (~11 min), but that ack was lost offline (issue 88). A crash on
  boot rolled back after one crash, an image signed with another key was refused (`bad_image`). Details:
  [Mower-Gateway-Plan](Mower-Gateway-Plan).

One-time setup (the bootloader can't be updated over the air, so this needs USB):

```powershell
mkdir keys
espsecure generate-signing-key --version 2 --scheme rsa3072 keys\ota_signing_key.pem
# back up keys\ota_signing_key.pem offline: without it, no more OTA (only a USB flash with a new key)
~\.platformio\penv\Scripts\pio.exe run -e gateway -t upload
tools\provision_cert.ps1 -Name mower-01   # client certificate (name = certificate CN)
```

An existing `sdkconfig.gateway` (`sdkconfig` for idf.py) keeps its old values: add the OTA block from `sdkconfig.defaults`
to it (or set the same options in menuconfig) before that build. The same goes for the two FreeRTOS options at the end
(`CONFIG_FREERTOS_USE_TRACE_FACILITY`, `CONFIG_FREERTOS_GENERATE_RUN_TIME_STATS`, needed for the `system.cpu` metrics):
delete `sdkconfig.gateway` or add them.

Each release:

```powershell
# bump version.txt (the device refuses the version it already runs)
tools\release.ps1 -Send    # PlatformIO build + sign, check version and signature, upload, send the ota command
tools\mqtt_watch.ps1      # gateway/state shows firmware, previous and partition; the final ack arrives on gateway/cmd/ack
```

The `ota` command: `{"id":"…","cmd":"ota","version":"0.2.5","file":"0.2.5.bin","size":851234}`.
`file` defaults to `<version>.bin`. It acks `accepted` at once, then (from the new image, after the restart)
`done`, or an error: `busy`, `same_version`, `low_signal`, `bad_image` (wrong project or version, bad
signature or SHA-256), `bad_size`, `download_failed`, `rolled_back`, `bad_request`, `failed`. The signed PlatformIO image of 0.3.0 / 0.3.1 (2026-11-10) is 729088 bytes
(RAM 20752/327680, flash 706493/4194304), plus a 64-byte header on each 4096-byte chunk.
The 0.3.1 download took 97 s (178 chunks). The esp-mqtt receive buffer is 8192 bytes so
that frame arrives in one event; a fragmented `MQTT_EVENT_DATA` is still reassembled.

## Layout

```
main/        the firmware: board, cell (esp_modem PPP), mqtt_link, remote_cmd, ota, gwstate (boot, state),
             metrics (catalogue, telemetry, monitor), usage (data counters); see Mower-Gateway-Architecture
tools/       at_bridge (AT console firmware), at_session.py (AT script), ppp_smoke (PPP + TLS test),
             mqtt_cmd.ps1 (remote commands), mqtt_watch.ps1 (read the gateway topics), release.ps1 (signed OTA release)
version.txt  firmware version (PROJECT_VER), bump it for every OTA release
components/  rmx_codec: pure C codecs (firmware chunk header; board link COBS/CRC-16 frames, reliable delivery, offline queue), no ESP-IDF includes, host-tested
test/        Unity host tests (pio test -e native, workflow host-tests)
certs/       ISRG Root X1/X2 PEMs (public CA roots for rmx.lt's Let's Encrypt chain)
```
